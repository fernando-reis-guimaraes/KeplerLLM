# KeplerLLM

Thin wrapper around the official AnythingLLM image with KeplerLLM-specific persistence, UI branding, model-picker cleanup, and controlled agent-authored Custom Skill staging.

## Fork changes

### Persistent AnythingLLM UI configuration

AnythingLLM writes UI-managed configuration to `/app/server/.env`. KeplerLLM stores that file at `${STORAGE_DIR}/.env` (normally `/app/server/storage/.env`) and exposes `/app/server/.env` as a symlink to it before starting the original AnythingLLM entrypoint.

This means the deployment only needs the normal named volume mounted at:

```text
/app/server/storage
```

No bind mount or separate file mount for `/app/server/.env` is required.

On the first KeplerLLM boot, if `${STORAGE_DIR}/.env` does not exist, the wrapper seeds it from the `.env` shipped in the upstream AnythingLLM image. Future changes made in the AnythingLLM UI are written through the symlink into the persistent volume.

### Model display name

The workspace model picker displays a KeplerLLM branding label instead of the underlying model identifier.

Default:

```text
Kepler AI
```

Override it at runtime with:

```text
KEPLERLLM_MODEL_DISPLAY_NAME=Your Name Here
```

This only changes the displayed label. The actual AnythingLLM provider and model configuration remain unchanged.

AnythingLLM already hides this picker from non-admin users in multi-user mode; this customization applies where the picker is visible, such as single-user mode and admin sessions.

The production root page is generated by AnythingLLM's `MetaGenerator`, so KeplerLLM patches that generator to load `/keplerllm-config.js` before the application bundle.

### Alphabetical OpenAI model picker

AnythingLLM groups OpenAI models by organization and sorts the organization names, but preserves the model order returned by the OpenAI `/v1/models` endpoint inside each group. That order is not alphabetical and can place snapshots from the same model family far apart.

KeplerLLM sorts models alphabetically by model name inside each OpenAI organization group before rendering the selector.

For example, snapshots such as:

```text
gpt-4o-2024-05-13
gpt-4o-2024-08-06
gpt-4o-2024-11-20
```

are displayed together in lexical order instead of inheriting the API response order.

This is a frontend-only change. It does not change model IDs, provider behavior, API requests, or the selected model.

The change is applied by `apply-keplerllm-branding.mjs` using an exact upstream source anchor, so an incompatible AnythingLLM upgrade fails the build instead of silently losing the sorting behavior.

### Agent-authored Custom Skills

KeplerLLM extends AnythingLLM's existing File System Access and Custom Skill mechanisms so the agent can author Custom Skill drafts without granting it write access to installed executable skills.

AnythingLLM's File System Access remains confined to:

```text
${STORAGE_DIR}/anythingllm-fs
```

KeplerLLM reserves this subdirectory for agent-authored skill drafts:

```text
${STORAGE_DIR}/anythingllm-fs/agent-skills
```

A draft uses the normal AnythingLLM Custom Skill layout:

```text
anythingllm-fs/agent-skills/send-email/
├── plugin.json
├── handler.js
└── README.md
```

Installed and executable Custom Skills remain in the normal administrative location:

```text
${STORAGE_DIR}/plugins/agent-skills
```

#### Security model

Agent-authored skills are staged, not executable.

The lifecycle is:

```text
File System Access
        ↓
anythingllm-fs/agent-skills/<hubId>
        ↓
Pending review
        ↓ admin enables the skill
plugins/agent-skills/<hubId>
        ↓
Executable Custom Skill
```

Important properties:

- A draft is always reported as inactive, even if its `plugin.json` contains `"active": true`.
- Pending drafts are not loadable by the agent runtime.
- Pending drafts are excluded from Scheduled Job tool selection.
- The Custom Skills UI labels drafts as `Pending review`.
- Enabling a draft through the admin/API Custom Skill toggle promotes it with a filesystem `rename` into `${STORAGE_DIR}/plugins/agent-skills` and sets it active.
- After promotion, File System Access can no longer modify the skill because it is outside `anythingllm-fs`.
- If the same `hubId` exists in both locations, the administrative `${STORAGE_DIR}/plugins/agent-skills` copy wins.
- Deleting a skill works for either an installed skill or a pending draft.

This creates a deliberate human approval boundary between code generation and code execution:

```text
WRITE → REVIEW → EXECUTE
```

rather than:

```text
WRITE → EXECUTE
```

#### Authoring a skill with the agent

1. Enable **Agent Skills → File System Access**.
2. Enable the file operations required for authoring, typically directory creation, writing, editing, reading, and listing.
3. Ask the agent to create the skill under `agent-skills/<hubId>` inside its File System Access root.
4. Review the generated `plugin.json`, `handler.js`, and any supporting files.
5. Open **Settings → Agent Skills → Custom Skills**.
6. The draft appears as **Pending review**.
7. Enable it to promote it into the executable Custom Skill directory.

Example request:

```text
Create a Custom Agent Skill named send-email under agent-skills/send-email.
Use the standard AnythingLLM plugin.json + handler.js layout.
Do not put credentials in source files.
Leave the skill inactive for review.
```

#### Implementation notes

The upstream AnythingLLM Custom Skill loader normally reads only:

```text
${STORAGE_DIR}/plugins/agent-skills
```

KeplerLLM patches the loader so it can also discover drafts from:

```text
${STORAGE_DIR}/anythingllm-fs/agent-skills
```

Discovery does not make a draft executable. Runtime loading and handler validation continue to use only the administrative plugin root. Promotion occurs only when the Custom Skill configuration endpoint is explicitly used to activate a pending draft.

The patch is applied at image build time by:

```text
apply-keplerllm-agent-skill-authoring.mjs
```

The patcher uses exact upstream source anchors and intentionally fails the build when those anchors change. This forces the fork customizations to be reviewed during an AnythingLLM version upgrade instead of silently applying an incorrect patch.

## Upstream version

The custom frontend and patched server files are built from the same stable AnythingLLM version used as the base image. The default is currently:

```text
1.16.1
```

Override the build version with `ANYTHINGLLM_VERSION` when intentionally upgrading.

Both KeplerLLM patchers fail the build if their expected upstream source anchors change:

```text
apply-keplerllm-branding.mjs
apply-keplerllm-agent-skill-authoring.mjs
```

This is intentional. Review and update the patches whenever the pinned AnythingLLM version changes.

## Build and publish

`.envrc` sets `IMAGE_TAG` to the current short Git commit hash. `compose.yaml` publishes both that immutable tag and `latest`.

After committing or pulling changes, set `IMAGE_TAG` from the current `HEAD` before building so a pasted multi-command block does not retain a stale direnv value:

```bash
export IMAGE_TAG="$(git rev-parse --short HEAD)"
docker compose build --push
```

Published images:

```text
cr.umapps.net/umapps/keplerllm:${IMAGE_TAG}
cr.umapps.net/umapps/keplerllm:latest
```

The Compose build builds for both `linux/amd64` and `linux/arm64`.

## CapRover

Use:

```text
STORAGE_DIR=/app/server/storage
```

Optionally customize the model label:

```text
KEPLERLLM_MODEL_DISPLAY_NAME=Kepler AI
```

Keep the named volume:

```text
anythingllm-storage -> /app/server/storage
```

No extra volume is required for agent-authored skill drafts; they live under the existing storage volume.

Existing AnythingLLM collector volumes can remain unchanged.
